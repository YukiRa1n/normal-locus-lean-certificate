# 可靠性依据：从类型检查到数学结论

## 所引用的可靠性结果

Mario Carneiro 的 *The Type Theory of Lean*（2019）在 Soundness 一节给出集合论模型的
可靠性定理，源文件中的标签是 `thm:sound`。参见作者的
[v1.0 原始源码](https://github.com/digama0/lean-type-theory/blob/v1.0/soundness.tex)
和 [发布版本](https://github.com/digama0/lean-type-theory/releases/tag/v1.0)。
作者 2025 年的 [HoTTEST 报告](https://www.math.uwo.ca/faculty/kapulkin/seminars/hottestfiles/Carneiro-2025-02-06-HoTTEST.pdf)
第 26/52 张幻灯片也陈述了这个结果。

其中与本说明相关的部分可概述为：若形式系统中有合法推导
\(\Gamma\vdash e:\alpha\)，则存在足够的宇宙界限 k，在所需不可达基数假设下，
对环境的每个合法解释 γ，都有

\[
\llbracket\Gamma\vdash e\rrbracket_\gamma
\in\llbracket\Gamma\vdash\alpha\rrbracket_\gamma.
\]

对命题而言，有证明项意味着其解释为真。这是语义可靠性，比单说“系统没有矛盾”更适合
解释数学证明的意义。它不是一个“终端退出码为 0，则任意自然语言命题为真”的定理。

## 必须区分的三个连接

1. **实现到推导**：具体内核接受了证明项，能否据此得到上述形式系统中的合法推导？
   这里依赖内核对规则的正确实现，包括导入、声明处理、归纳类型和定义等价。
2. **推导到语义**：在可靠性结果覆盖的形式系统和模型假设下，合法推导在模型中成立。
3. **语义到文稿**：Lean 中的对象、输入和结论是否准确表达文稿的数学含义？
   这需要检查定义与量词，并对照外部来源。

2019 年论文不是对本仓库使用的 Lean 4.28.0 二进制的逐行正确性证明。
本工程也没有构造“此次 Lean 4 证明项 → 论文形式系统”的保型翻译证书。
因此本文把适用于所用逻辑的可靠性、内核实现正确性及语义对应明确列为信任前提，
不把它们冒充成本仓库程序已经证明的结果。

[Lean4Lean 论文](https://arxiv.org/abs/2403.14064)研究了独立检查及形式化元理论；
不能仅凭项目名称就声称具体版本的内核与模型可靠性已全部被机器证明。
作者的 2025 年报告还区分了可执行检查器与实现正确性证明的进度。
该报告第 48/52 张幻灯片还说明，在形式化相关的唯一类型和定义反演结果时发现了
一个证明缺口。这是对当时报告内容的说明，不是对后来项目进展的断言。
因此本文引用 Soundness 的准确表述和模型路线，同时显式保留适用逻辑的可靠性前提；
不声称旧论文或本项目已经提供覆盖 Lean 4.28.0 全部实现的机器可靠性证书。

## 本仓库的相对可信性归约命题

记 L 为实际的 `External.Library`，P 为实际的 `NormalLocusTheorem`，p 为本仓库证书。
下述归约是本说明对可靠性原理的应用，不是伪称某篇文献中另有同名定理：

> 若所用检查器对相关证明项正确实现了一个可靠的逻辑，冻结并审阅的定义准确表达
> 文稿，13 项外部输入在这个解释中均成立，且 p 被正确检查为 L → P，
> 则文稿中的 NL 结论成立。

理由是：检查得到 L → P 的合法证明，可靠性给出其语义有效性；外部结果及其接口转换
给出 L 的有效性；应用蕴含消去得到 P，最后由语义对应得到文稿结论。

这个论证把组合步骤的逐行人工检查交给内核，但没有消除原始结果到接口的人工数学工作。
特别是 `External.Library` 没有被构造出来，不能把条件式证书误报为无条件定理。

## 程序能验证的条件

| 条件 | 检查方法 | 准确含义 |
|---|---|---|
| 检查的是审阅过的源文件 | `manifest.json` 的 SHA-256 与文件集合核对 | 检测版本漂移；哈希自身不能证明数学正确 |
| README 展示的是实际声明 | 从源码提取后逐字比较 README、`target.md`、`inputs.md` | 防止展示文本与接受检查的源码不一致 |
| 恰好 13 项已登记输入 | 结构字段与登记逐项比较 | 不等于证明 13 项输入为真 |
| 证书确实为 theorem 且结论正确 | 声明种类检查、与 L → P 的定义等价检查 | 拒绝错误目标、额外条件或空壳证书 |
| 没有漏证或额外公理 | 传递公理白名单：`propext`、`Classical.choice`、`Quot.sound` | 拒绝 `sorryAx`、自定义公理和本版本的 `Lean.trustCompiler` |
| 已存储证明能再次被内核接受 | `scripts/Replay.lean` 在空环境、trust level 0 重放完整声明依赖闭包 | 重新检查主定理和所需定义、定理、归纳声明；使用相同官方内核 |
| 检查失败不会被当成成功 | 错目标、额外公理、`sorry`、额外前提等负向测试 | 验证这些具体失效模式，不是检查器正确性的形式化证明 |

输入语义及原引用转换在 [semantic-review.md](semantic-review.md) 中逐项审阅。
验证结果把它标记为 `MANUAL_REVIEW`，把可靠性及实现标记为 `TRUST_ASSUMPTION`；
不会因为所有可执行测试通过就把这两种状态改成 `PASS`。

## 检查强度的边界

Lean 官方的 [Validating a Lean Proof](https://lean-lang.org/doc/reference/latest/ValidatingProofs/)
区分了构建、公理检查、内核重放和隔离环境中的 comparator / 外部检查器，并明确保留
语义审阅和实现方面的信任条件。本仓库执行前述构建、公理及新环境重放，
没有声称已经运行 comparator 或独立类型检查器，也没有声称自动排除了所有恶意攻击。

这一限制与本次可信性论证直接相关：固定的 Lean 4.28.0 早于
[4.33.0 公布的内核可靠性修复](https://lean-lang.org/doc/reference/latest/releases/v4.33.0/)。
这不证明本项目用了相关漏洞，但意味着不能把版本固定或同一内核重放当成独立排错。
本文不升级原证明环境；若日后进行版本迁移或独立检查，应发布新的验证记录，
并单独报告通过范围。

当前证据支持“在公开的数学与实现前提下，组合推导经过可重现检查”。
它不支持“所有充分条件都已经由程序证明，因此完全不再需要任何信任”的说法。
